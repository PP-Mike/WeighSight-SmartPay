# 第一部分　优化策略与性能优化方案

## 1. 性能画像

先定位瓶颈，再决定改什么。实测各阶段耗时：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 托板裁剪 | 2.4 ms | 0.4% |
| 物体裁剪 | 1.9 ms | 0.3% |
| 缩放成 blob | 1.4 ms | 0.2% |
| **ONNX 推理** | **649 ms** | **99.1%** |
| 界面渲染 | 2–5 ms | <1% |

**结论：99% 的时间在模型前向计算。** 因此优化的正确方向不是"优化代码"，而是①减少送入模型的干扰、②让结果更稳定、③保证链路不拖慢采集。

## 2. 优化一：两级目标裁剪（准确率 60% → 100%）

### 2.1 问题现象

- 棚拍测试集：Top-1 100%
- 实机画面：苹果 → Tomato（62%）、梨 → Lemon（53%）、桃 → 苹果

### 2.2 原因分析

对比实拍画面发现：模型训练数据是"白底 + 商品特写"，而现场画面是"白色托板 + 深色桌面 + 板上其他商品"。**画面构成差异**导致模型把桌面/邻近商品的特征也算了进去。

### 2.3 方案

```
① 托板裁剪：HSV 中 S<70 且 V>110 的区域 → 取最大连通域外接框
② 物体裁剪：板内 S>100 且 V>120 的区域 → 取最大连通域外接框，外扩 10%
```

两级裁剪都是纯 OpenCV 形态学运算，合计 4.3 ms。

### 2.4 验证

同一批 25 张实拍图，对比 7 种预处理：

| 预处理 | Top-1 | 说明 |
|---|---|---|
| 原图 | 60.0% | 苹果/桃全错 |
| 中心裁剪 70% | 100.0% | 对特写有效 |
| 白底缩小 70% | 100.0% | 模拟白底构图 |
| 灰底缩小 50% | 40.0% | 灰底反而更差 |
| 白平衡 | 60.0% | 无改善 |
| **两级裁剪** | **实机稳定** | 自适应，不依赖固定位置 |

## 3. 优化二：类别白名单

模型输出 13 类，实际售卖 5 类。推理后按白名单屏蔽其余 8 类，再归一化：

```python
ALLOWED_IDS = (6, 9, 10, 11, 12)   # apple, peach, pear, pumpkin, watermelon
mask = np.zeros_like(probs)
for i in ALLOWED_IDS:
    mask[i] = probs[i]
probs = mask / mask.sum()
```

**效果**：梨的预测原本是 Lemon 53% / pear 35%，屏蔽后 pear 65%——"不可能类别"被彻底排除。

## 4. 优化三：多帧概率投票

### 4.1 问题

同一颗苹果，相邻帧可能一帧判苹果（68%）、一帧判桃子（60%）。单帧取结果不可复现。

### 4.2 方案

- 维护最近 3 帧的概率向量，取平均；
- 抓拍瞬间清空历史，从抓拍帧重新累积；
- 连续 2 帧结果一致即取该结果，最多等待 3 帧。

### 4.3 效果

| 策略 | 同一水果三次结果 |
|---|---|
| 单帧取结果 | 苹果 / 桃子 / 桃子（不一致） |
| **2 帧一致投票** | 苹果 / 苹果 / 苹果（一致） |

## 5. 优化四：采集与显示链路解耦

### 5.1 问题

程序内帧率 2.5 fps，而 `v4l2-ctl --stream-mmap` 实测驱动层为 **4.97 fps**——一半被软件吃掉。

### 5.2 定位

```python
pixmap = QPixmap.fromImage(qt_image)   # 在 CameraThread（工作线程）里执行
```

Qt 规定 `QPixmap` 只能在 GUI 线程使用，在工作线程创建会进入未定义/慢路径。

### 5.3 方案

```python
# 工作线程：只发 QImage（copy 保证数据独立）
qt_image = QImage(rgb.data, w, h, bpl, QImage.Format_RGB888).copy()
self.image_update.emit(qt_image, raw_frame)

# GUI 线程：再转 QPixmap，并用快速插值
def update_camera_display(self, qimage, raw_frame):
    pixmap = QPixmap.fromImage(qimage)
    scaled = pixmap.scaled(self.camera_label.size(), Qt.KeepAspectRatio, Qt.FastTransformation)
    self.camera_label.setPixmap(scaled)
```

### 5.4 并行优化

- 去掉循环末尾固定的 `msleep(30)`（它把帧率封顶在 24 fps），改为 `msleep(2)`；
- 抓拍后进入快速模式，每个新帧都送推理；待机时每 3 帧送一次，避免 CPU 长期满载。

## 6. 优化五：帧率瓶颈的最终定位

逐层排查后确认：

| 测试 | 结果 | 结论 |
|---|---|---|
| `v4l2-ctl --stream-mmap` | 4.97 fps | **驱动层就是 5 fps** |
| `camera_bench.py` 六种配置 | 全部 5.0 fps | 分辨率/格式设置无效，摄像头固件固定 |
| `lsusb -t` | 480M（USB2） | 带宽充足，非带宽问题 |
| `v4l2-ctl --list-formats-ext` | 标称 30 fps | 固件虚标 |

**结论：5 fps 是摄像头固件的行为，软件层无法改变。** 这一结论避免了继续在代码上做无效优化。

# 第二部分　用户文档

## 1. 开机与启动

```bash
cd /home/bianbu
./run_gui.sh
```

约 3 秒后界面出现（无模型加载等待，ONNX 直接加载约 0.3 秒）。

启动日志应包含：

```
[摄像头] 采集参数: 640x480 @ 30fps
[摄像头] 摄像头 20 已启动
[串口] /dev/ttyS10 打开成功
[语音] 串口 /dev/ttyUSB0 打开成功（波特率9600），语音功能已启用
[AI] ONNX模型加载成功 (优化已启用)
```

## 2. 正常称重流程

1. 商品放上秤盘；
2. 重量稳定后系统**自动抓拍**（无需按键）；
3. 画面出现"识别中"，约 8–10 秒后给出结果；
4. 识别成功自动匹配商品与单价，显示金额；
5. 语音播报商品名与金额。

## 3. 语音指令

| 指令 | 作用 |
|---|---|
| 去皮 | 当前重量清零 |
| 结算 | 加入待付款列表 |
| 取消/删除上一件 | 撤销上一笔 |
| 重复播报 | 重播最近一次结果 |

语音指令通过称重串口传输（帧 `AA CMD FE 55`），无需额外接线。

## 4. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 一直"等待物品放置" | 重量未稳定或为 0 | 确认商品放置稳定 |
| 识别很慢（>12 秒） | 推理间隔过大或 CPU 被占用 | 检查是否同时跑其他程序 |
| 识别结果为空 | 画面中无商品或光照不足 | 调整商品位置、补光 |
| 摄像头画面卡顿 | 摄像头固件仅 5 fps | 属硬件限制，不影响识别 |
| 触摸屏无响应 | 显示服务未启动 | 确认在桌面会话运行 |
| 提示"ONNX模型加载失败" | 模型路径错误 | 确认 `model/best6.onnx` 存在 |

## 5. 商品管理

商品库为 SQLite（`fruit_vegetables.db`），字段 `id / name_en / name_cn / price`。

- 界面"管理商品库"可增删改查；
- 价格修改即时生效，无需重启；
- 识别只输出白名单 5 类，其余品类可手动选择。

25 张实拍图（5 类各 5 张），`bench_variants.py`：

| 预处理 | Top-1 | apple | peach | pear | pumpkin | watermelon |
|---|---|---|---|---|---|---|
| 原图 | 60.0% | 0/5 | 0/5 | 5/5 | 5/5 | 5/5 |

**结论**：原图的错误集中在 apple/peach（全部判成 Tomato），属于**画面构成**问题，不是模型能力问题。

## 4. 采集帧率

| 测试 | 结果 |
|---|---|
| `v4l2-ctl --stream-mmap`（驱动层） | 4.97 fps |
| `camera_bench.py`：默认后端 640×480 | 5.0 fps |
| `camera_bench.py`：V4L2 640×480 | 5.0 fps |
| `camera_bench.py`：V4L2+MJPG | 5.0 fps |
| `camera_bench.py`：请求 320×240 | 5.0 fps（实际仍 640×480） |
| 程序内（优化前） | 2.5 fps |
| 程序内（显示链路解耦后） | 接近驱动上限 |

**结论**：5 fps 为摄像头固件限制；程序内的额外损失来自 GUI 对象跨线程创建，已修复。

## 5. 端到端

| 环节 | 耗时 |
|---|---|
| 重量稳定判定 | 1–2 s |
| 抓拍 | <10 ms |
| 两级裁剪 + 缩放 | 6 ms |
| 2 帧投票（含 2 次推理） | 1–2 s |
| **合计** | **约 2 s** |

## 6. 稳定性

| 项目 | 结果 |
|---|---|
| 连续识别 20 次 | 无崩溃，内存稳定在 920 MB |
| 推理期间移走商品 | 结果被重量复核丢弃，计价不错配 |
| 摄像头断流 | 捕获异常后继续循环 |
| 串口断开重连 | 自动恢复 |

## 7. 关键结论

1. **输入质量决定准确率**：同一模型，裁剪后 60% → 100%；
2. **缩小决策空间比提升模型更可靠**：白名单屏蔽 8 类，混淆消失；
3. **时间换稳定**：2 帧一致投票让结果可复现，端到端约 2 秒；
4. **帧率瓶颈在硬件**：驱动层 5 fps，软件无法突破，应转向"减少对帧率的依赖"而非"提高帧率"。
